# iOS setup

The Xcode project in `ios/App` is generated by Capacitor and is committed, and
so now are the two things this document used to ask you to do by hand: the App
Group, and the two Share Extension targets. They were added with the
`xcodeproj` gem rather than through the Xcode UI, so they live in
`project.pbxproj` and survive a fresh clone.

What is left is signing, which cannot be committed — see [Signing](#signing).

```sh
npm install
npm run sync        # vite build + cap sync ios
npx cap open ios    # opens ios/App/App.xcodeproj
```

Re-run `npm run sync` after every web change; Xcode serves the copy in
`ios/App/App/public`, not `dist`.

## What is already wired

### The App Group

`group.com.zaremy.inspo`, declared in three entitlement files — `App`,
`InspoShare`, `InspoSharePage` — next to the project, and named once in code in
`ios/native/InspoShared.swift`:

```swift
static let appGroupId = "group.com.zaremy.inspo"
```

If you change the identifier, change it in all four places.

### The two Share Extension targets

Whether a page has a DOM is not something the app gets to decide, so Inspo
ships two share entries and lets the share sheet ask which one you meant:

| Target | Bundle id | Shows up for | Captures |
| --- | --- | --- | --- |
| `InspoShare` — "Inspo" | `com.zaremy.inspo.InspoShare` | any image, from any app | the picture |
| `InspoSharePage` — "Inspo Page" | `com.zaremy.inspo.InspoSharePage` | a web page, from Safari | the markup |

Both run the same `ShareViewController` and write into the same queue; only
their `Info.plist` differs. The page plist's
`NSExtensionJavaScriptPreprocessingFile` key is what makes Safari run the DOM
serializer in the tab; the image plist deliberately has no such key.

### Target membership

| File | App | InspoShare | InspoSharePage |
| --- | --- | --- | --- |
| `InspoShared.swift` | yes | yes | yes |
| `ShareIntakePlugin.swift` | yes | no | no |
| `MainViewController.swift` | yes | no | no |
| `ShareViewController.swift` | no | yes | yes |
| `share-preprocess.js` | no | no | yes (Copy Bundle Resources) |

`share-preprocess.js` is generated — run `npm run build:preprocess` (or
`npm run sync`, which includes it) after changing `src/lib/domSnapshot.ts`, and
never edit it by hand. It is in the extension's **Copy Bundle Resources** phase
rather than Compile Sources, because Safari loads it by name.

## Signing

The only step that is still yours, because it needs an Apple developer team and
provisioning that only exists on your Mac.

All three targets are set to `DEVELOPMENT_TEAM = 7Z8N956AQ2` with automatic
signing. Building for the **simulator** needs nothing further. Building for a
**device** requires Xcode to register three App IDs and the App Group with
Apple, which it will offer to do the first time you build to hardware — accept
the prompt, or run a device build once with `-allowProvisioningUpdates`.

App Groups need a paid Apple Developer Program membership. A free personal team
cannot provision one, and the share sheet is the whole point, so this is not
optional for device use.

## URL scheme

Registered in `ios/App/App/Info.plist` as `inspo://`. The extension opens
`inspo://shared`. Nothing to do unless you rename the scheme, which lives next
to the App Group id in `InspoShared.swift`.

## How a share actually flows

```
Screenshot in any app
  -> Share sheet -> Inspo
  -> ShareViewController writes the image into the App Group queue folder
  -> extension asks iOS to open inspo://shared
  -> app foregrounds, ShareIntakePlugin drains the queue
  -> capture sheet opens, already filled in with the last used FROM and FOR
  -> Save
```

```
Share a screenshot  -> Inspo       ->  <uuid>.png
Share a page        -> Inspo Page  ->  <uuid>.inspodom     (app draws the cover)
```

Whichever button was tapped, the material lands in the same queue and the same
capture sheet. The sidecar is named after the image it belongs to, so the
plugin pairs them up and deletes them together. A page-only share still becomes
a normal capture, because the app renders the markup to an image rather than
leaving a blank tile on the wall.

## Three traps, all paid for on a simulator

**The extension does not reliably foreground the host app.** `extensionContext.
open` is allowed to refuse, and `ShareViewController` falls back to walking the
responder chain for `openURL:` — the usual workaround, which Apple has been
steadily closing. On the simulator it does not work at all: the share sheet
dismisses and you stay in Photos. Nothing is lost, because the screenshot is
already in the queue and the next launch drains it, but the advertised gesture
is *share, tag, save* and what you may actually get is *share, open Inspo, tag,
save*. Verify this one on hardware before believing either outcome.

**Capacitor does not auto-register an app-local plugin.** `registerPlugins()`
registers its own built-ins plus whatever `cap sync` writes into
`capacitor.config.json` as `packageClassList` — and that list is generated from
npm packages. `ShareIntakePlugin` lives in the app target, so it is in neither
set. Nothing errors: `isPluginAvailable('ShareIntake')` simply returns false and
`drainPendingShares()` returns an empty list forever. It is registered
explicitly in `MainViewController.capacitorDidLoad()`. Do not try to fix this by
editing `capacitor.config.json` — every `cap sync` regenerates it.

**`SceneDelegate` builds the root view controller in code**, so pointing
`Main.storyboard` at a custom class does nothing. Both are set to
`MainViewController` now, but the storyboard is the decoy: the line that
actually decides is `window?.rootViewController` in `SceneDelegate.swift`.
