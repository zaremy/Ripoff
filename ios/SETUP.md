# iOS setup

The Xcode project in `ios/App` is generated by Capacitor and is committed. Two
things still have to be done by hand in Xcode, because both need an Apple
developer team and provisioning that only exists on your Mac:

1. registering the App Group the app and its extensions talk through
2. creating the two Share Extension targets

Until step 2 is done the app still works — you add screenshots with the **+**
button. Step 2 is what turns the iOS share sheet into the capture path.

## 0. Build the web app first

```sh
npm install
npm run sync        # vite build + cap sync ios
npx cap open ios    # opens ios/App/App.xcodeproj
```

Re-run `npm run sync` after every web change; Xcode serves the copy in
`ios/App/App/public`, not `dist`.

## 1. App Group

Both targets read and write one shared folder. Its identifier is defined once,
in `ios/native/InspoShared.swift`:

```swift
static let appGroupId = "group.com.zaremy.inspo"
```

In Xcode, for the **App** target: *Signing & Capabilities* → **+ Capability** →
*App Groups* → add `group.com.zaremy.inspo`. Repeat for **both** Share
Extension targets once they exist in step 2.

If you change the identifier, change it in `InspoShared.swift` too — nothing
else references it.

## 2. Add the native sources

The files in `ios/native/` are staged, not yet part of any target. Drag them
into Xcode with *Add Files to "App"* and set target membership as follows:

| File | App | InspoShare | InspoSharePage |
| --- | --- | --- | --- |
| `InspoShared.swift` | yes | yes | yes |
| `ShareIntakePlugin.swift` | yes | no | no |
| `ShareViewController.swift` | no | yes | yes |
| `share-preprocess.js` | no | no | yes (Copy Bundle Resources) |

`share-preprocess.js` is generated - run `npm run build:preprocess` (or
`npm run sync`, which includes it) after changing `src/lib/domSnapshot.ts`, and
never edit it by hand. It has to land in the extension's **Copy Bundle
Resources** build phase, not Compile Sources; Safari loads it by name.

`InspoShared.swift` belongs to both because the queue folder is the contract
between the two processes.

### Creating the two Share Extension targets

Whether a page has a DOM is not something the app gets to decide, so Inspo
ships two share entries and lets the share sheet ask which one you meant:

| Target | Shows up for | Captures |
| --- | --- | --- |
| `InspoShare` — "Inspo" | any image, from any app | the picture |
| `InspoSharePage` — "Inspo Page" | a web page, from Safari | the markup |

Both run the same `ShareViewController` and write into the same queue; only
their `Info.plist` differs. Create each with *File* → *New* → *Target…* →
**Share Extension**, accepting the scheme when Xcode offers it, then for each:

- Delete the `ShareViewController.swift` and `MainInterface.storyboard` that
  Xcode generates — neither extension has UI of its own.
- Replace the generated `Info.plist` with the matching one from `ios/native/`:
  `ShareExtension-Image-Info.plist` for `InspoShare`,
  `ShareExtension-Page-Info.plist` for `InspoSharePage`. The page plist's
  `NSExtensionJavaScriptPreprocessingFile` key is what makes Safari run the DOM
  serializer in the tab; the image plist deliberately has no such key.
- Remove the `NSExtensionMainStoryboard` key if Xcode added one; the principal
  class key in the provided plists replaces it.
- Set the deployment target to match the app's.
- Add the App Group from step 1.

`CFBundleDisplayName` is what the share sheet shows, so keep the two names
distinct or you will not be able to tell the buttons apart.

## 3. URL scheme

Already registered in `ios/App/App/Info.plist` as `inspo://`. The extension
opens `inspo://shared` so a share brings the app straight to the capture
sheet. Nothing to do unless you rename the scheme, which lives next to the App
Group id in `InspoShared.swift`.

## How a share actually flows

```
Screenshot in any app
  -> Share sheet -> Inspo
  -> ShareViewController writes the image into the App Group queue folder
  -> extension opens inspo://shared
  -> app foregrounds, ShareIntakePlugin drains the queue
  -> capture sheet opens, already filled in with the last used FROM and FOR
  -> Save
```

## Capturing the page as well as the picture

iOS never hands over pixels and DOM in one gesture, which is why there are two
buttons rather than one that guesses:

```
Share a screenshot  -> Inspo       ->  <uuid>.png
Share a page        -> Inspo Page  ->  <uuid>.inspodom     (app draws the cover)
```

Whichever button was tapped, the material lands in the same queue and the same
capture sheet. The sidecar is named after the image it belongs to, so the
plugin pairs them up and deletes them together; on the rare share that carries
both, one capture comes out with both halves. A page-only share still becomes a
normal capture, because the app renders the markup to an image rather than
leaving a blank tile on the wall.

If iOS refuses to open the host app — it is allowed to, and the extension does
not treat that as an error — the screenshot simply stays in the queue and is
picked up the next time Inspo is opened. Nothing is ever lost, and nothing in
this path touches the network.
